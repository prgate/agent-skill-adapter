# Спецификация: перенос набора ассетов Claude Code в рабочее состояние в Antigravity

## Задача

Человек собрал набор ассетов в формате Claude Code — скиллы, субагентов, команды,
файлы-правила, манифест плагина — и хочет пользоваться им в Antigravity. Сегодня он
копирует файлы по документированным путям и остаётся один на один с тишиной: часть
набора среда видит, часть не видит, и никто ему об этом не говорит. Проверено на ките
prgate-kit: скиллы и `GEMINI.md` дошли, четыре субагента невидимы из-за одного значения
поля, пять команд не работают ниоткуда, пять файлов правил лежат там, где их не читает
ничто. Ни одной строки об этом он не получил.

Разрыв между «лежит на диске» и «работает в среде» не видит никто, и закрыть его
копированием нельзя: копирование уже есть, и его недостаточно.

## Решение

`convert` перестаёт быть командой про одну папку скилла и становится командой про набор.
На входе — состав: папка скиллов, папка субагентов, папка команд, файлы правил, манифест
плагина; любая часть может отсутствовать. На выходе — три вещи:

1. **Переведённый набор.** Значения полей с закрытым набором допустимых значений
   (`model`, имена инструментов) приводятся к словарю целевой среды по таблице перевода.
   Ссылки внутри перенесённых файлов ведут туда, куда файлы легли.
2. **Сводный отчёт.** Одна строка на каждую сущность и на каждый файл: перенеслось —
   куда; не перенеслось — почему и что сделать руками; переведено — что было, что стало,
   по какому правилу. Вердикт прогона — худший по набору.
3. **Рабочее состояние.** По умолчанию сборка идёт в `--out`, и команда печатает готовую
   строку установки. Живой корень `~/.gemini/` конвертер трогает только по явному
   `--install`, показав план до первой записи.

Ни одно имя из образца в код не попадает. Конвертер читает то, что лежит на входе, и
спрашивает про это описания сред; правило перевода выводится из описания (закрытый набор
значений объявлен в описании среды), а отображение значений — из отдельно версионируемого
файла правил.

## Решения по реализации

**1. Закрытый набор значений — в описании среды; отображение значений — в файле правил.**
`Capability` получает необязательное поле `values: list[str] | None` — набор значений,
который документация среды называет явно. Отсутствие набора значит «документация набора
не называет», а не «любое значение годится»: без набора перевод не применяется и запись
остаётся `unknown`. Почему так: правило «значение вне набора требует перевода» должно
опираться на документ, иначе оно выведено из наблюдения за одним набором — ровно то, что
бриф запрещает.

**2. Файл правил перевода — отдельный версионируемый артефакт (FR-6).**
`rules/<name>-<version>.yaml`, со своим `rules_version`, объявляющий:
отображения значений (`value_maps`, по id записи описания), отображения имён инструментов,
список игнорируемого (`ignore`), правило по недокументированному файлу (`undocumented`),
и список того, к чему применяется подстановка ссылок (`rewrite`), с явным перечнем
неприкосновенного. Поле `tool_names` уходит из `EnvSpec` в правила: оно и есть отображение,
а не свойство среды. Данных не теряется — оно пусто во всех трёх описаниях.

**Отображение имён инструментов содержит только пары, которые документация поддерживает.**
Для пары Claude Code → Antigravity документация цели называет `view_file`, `grep_search`,
`run_command`; отсюда `Read` → `view_file`, `Grep` → `grep_search`, `Bash` → `run_command`.
Имя источника, для которого документированной пары нет (`Glob`, `Edit`, `Write`,
`SendMessage` и любое другое), **не выдумывается и не выбрасывается**: оно остаётся в файле
как есть и получает строку отчёта с причиной «в словаре целевой среды нет соответствия» и
советом убрать имя или сопоставить его руками. Причина, по которой это не тишина: цель
предупреждает, что неизвестное имя инструмента может подвесить субагента при вызове, — на
обнаружение это не влияет, на работу влияет. Придумывать пару по созвучию запрещено тем же
правилом, что и всё остальное: правило выводится из описания, а не из догадки.

**3. Вход задаётся составом.** Повторяемые опции `--skills DIR`, `--agents DIR`,
`--commands DIR`, `--rules PATH`, `--plugin FILE`. Позиционный аргумент «одна папка скилла»
остаётся и значит ровно то же, что и раньше. Почему так: набор, разложенный иначе, должен
конвертироваться теми же правилами, а раскладка образца ничего не доказывает про другие.

**3а. Что в названной папке отказ, а что строка.** Отказ — только про то, что назвал человек:
названного пути нет, его не прочитать. Всё, что найдено внутри названной папки и не похоже на
сущность — посторонний каталог без `SKILL.md`, файл не того формата, папка-симлинк, которую не
обходим ради защиты от петли, — становится строкой отчёта «никто не объявлял», а не роняет прогон.
Иначе чужая раскладка с каким-нибудь служебным каталогом рядом со скиллами получает отказ вместо
переноса всего остального, и правило «ни один файл не исчезает без строки» нарушается в обе стороны
сразу: прогона нет, строки тоже нет.

**4. Идентификаторы записей.** Сущность спрашивает описания про свои id: скилл —
`skill.frontmatter.<key>`, `skill.dir.<name>`, `skill.top.<name>`; субагент —
`subagent.frontmatter.<key>`, `subagent.system-prompt-body`; правило — запись **места**, которое
называет цель (`rules.project` / `rules.user` по `--scope`), а не выдуманный `rules.file`: сущность,
для которой цель называет корень, перенесена, и строка отчёта обязана это отражать;
манифест — `settings.file.plugin-manifest`; команда — `command.file` (записи нет ни в
одном описании, и это её ответ). Конвертер по-прежнему ничего не сравнивает сам и не
держит списка известных имён.

**5. Происхождение строки отчёта.** Сегодня «нет записи ни в одном описании» печатается и
там, где запись знает цель. Разделяется на три случая: знают обе, знает только цель,
не знает никто. Это первая правка трека и ни от чего не зависит.

**6. Назначение.** Без `--install` — только `--out`, плюс печать готовой команды установки.
С `--install` — раскрытие тех же записей `layout` относительно живых корней, план в
поток ошибок до первой записи, те же проверки коллизий и выхода за корень.
`--install` вместе с `--out` — отказ: назначение одно, а не два. Отдельного «сухого»
флага нет — план печатается всегда, и это ровно то, чего просили.

**Файлы команд в сборку не попадают ни при каком назначении.** Записи `commands.*` в
описании цели нет, класть их некуда, и копирование «на всякий случай» создало бы ровно
ту тишину, которую трек закрывает. Каждая команда набора получает строку отказа.

**7. Подстановка ссылок.** Переписываются только ссылки, ведущие на файлы, которые этот же
прогон переместил, и только в файлах, которые названы в правилах. `CHANGELOG.md` и всё,
что правила не называют, не трогается ничем.

**8. `references/` и `resources/` в описании Antigravity.** `Source` получает
`retrieved_from: "web" | "shipped"` (по умолчанию `web`); `freshness` перепроверяет только
`web`. Это позволяет описанию отражать оба источника — публичную страницу и скилл,
поставляемый с CLI, — не ломая единственную команду, которая ходит в сеть.
`resources/` уже есть в `layout` и остаётся; `references/` добавляется рядом как
равноправная. Обе прочитаны средой в T0, поэтому переименования бандлов не происходит
и ни одна ссылка внутри скиллов по этой причине не переписывается.

**9. Манифест плагина — что собирается в успешном случае.** *Исправлено 2026-09-16 по `D02`:
бриф описывал формат цели неверно.* Поставляемая с CLI документация (`agy-customizations/docs/plugins.md`,
секция «Manifest (`plugin.json`)») говорит, что манифест цели несёт ровно два поля — `name`
(необязательное, по умолчанию имя папки) и `disabled` (необязательное), — а скиллы, правила,
`hooks.json` и `mcp_config.json` среда находит **по структуре папки плагина**, а не по полям
манифеста. Поэтому переписывание манифеста — это `plugin.json` с `name`, плюс раскладка частей
плагина по его папке; а `description`, `version`, `homepage`, перечни скиллов и правил из
манифеста источника места в формате цели не имеют и дают по строке отчёта каждое.

Чтобы это можно было спросить у описания, а не знать в коде, описание цели объявляет поля
манифеста отдельными записями (`settings.file.plugin-manifest.<field>`) с источником-поставкой —
иначе список полей вендора оказался бы вписан в конвертер, что конвенции проекта запрещают. Кусок берётся последним; не влез в прогон —
откладывается строкой в отчёте с указанием, что именно осталось несделанным.

**10. Откуда берётся `rules.project` и чего требует эта папка.** Запись уже есть в описании
Antigravity (`rules.project` → `.agents/rules/`), объявлять её не нужно. Читается ли папка —
**проверено запуском 2026-09-16 (D01)**: читается, но только если файл несёт заголовок
`trigger: always_on`. Без заголовка среда молчит — правило есть на диске и не действует.
Поставляемая с CLI документация говорит это прямо: «Rules with `trigger: model_decision`
behave similarly. Only `always_on` rules are loaded unconditionally», — и она же перечисляет
`.agents/rules/*.md` среди путей правил, тогда как её собственная страница `rules.md`
называет только `GEMINI.md`/`AGENTS.md`. Два источника расходятся, и описание обязано
отражать оба, как и в случае с `references/`.

Следствие для переноса: файл правил, переложенный в `rules.project`, получает заголовок
с `trigger: always_on`. Значение берётся из закрытого набора, объявленного в описании среды,
а сам заголовок добавляется по правилу из файла правил перевода — ни то, ни другое не
вписывается в код. Файл, у которого заголовок уже есть, не переписывается: добавляется
только недостающее.

**11. Процедура доказательства запуском.** Три уровня, сверху вниз, первый сработавший
и есть доказательство:
1. **Без модели.** `agy agents` перечисляет субагентов напрямую — приёмка R15/R34.
   (Сегодня на установленном образце печатает пусто, что и есть измеряемая проблема.)
2. **Неинтерактивный прогон.** `agy --mode plan -p='...'` и `agy -p='...'` с вопросом,
   ответ на который требует прочитать перенесённый файл: цитата якорной строки или явный
   отказ «файла нет». Ответ «да, вижу» доказательством не считается.
3. **Если ни один не сработал** — сказать прямо, какой способ пробовали и что он дал.
   Чтение кода за проверку не выдаётся ни при каких обстоятельствах.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `envspec/model.py` | формой описания среды | `Capability.values`, `Source.retrieved_from` | — (схема) |
| `rules.py` | правилами перевода и их версией | `load(path) -> Rules`; `Rules.version`, `Rules.value_of(entry_id, value)`, `Rules.tool_name(name)`, `Rules.ignored(rel)`, `Rules.rewritable(rel)`, `Rules.undocumented` | форму YAML правил |
| `assets.py` | чтением набора с диска | `read(Inputs) -> tuple[Asset, ...]`; `Asset(kind, path, name, frontmatter, findings)` | обход папок, разбор заголовков, применение списка игнорируемого |
| `convert.py` | оценкой, планом и сборкой | `convert(...) -> Conversion` | таблицу вердиктов, раскрытие путей, запись |

Швы для тестов — три: `rules` (файл → выборки), `assets` (папка → сущности),
`convert` (набор → отчёт). Существующие швы `normalize`, `loader`, `gaps`, `freshness`
не двигаются.

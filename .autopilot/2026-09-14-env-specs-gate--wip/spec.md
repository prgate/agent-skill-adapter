# Спецификация: описания сред и гейт FR-48

## Задача

Скилл, написанный под Claude Code, в Google Antigravity запускается молча и ведёт себя иначе:
чужая среда пропускает незнакомые поля. Прежде чем писать перенос, надо знать по документам,
а не по памяти: что именно Antigravity не воспроизводит из восемнадцати полей Claude Code,
субагентов и hooks. Если не воспроизводит ничего — продукт сводится к копированию файлов,
и делать его незачем (FR-48).

Сейчас этого знания нет ни в каком виде: ни данных, ни способа проверить, что они не устарели.

## Решение

Появляется три вещи.

1. **Два описания сред** — машиночитаемые YAML-файлы: Claude Code (источник) и Antigravity
   (цель). У каждой записи о свойстве — ссылка на официальную документацию, якорь раздела,
   хеш нормализованного текста этого раздела, дата проверки и версия среды.
2. **Загрузчик** — библиотека, которая читает эти файлы, проверяет их схему, выбирает описание
   по заявленной версии среды, отвечает «неизвестно» на свойство, которого в описании нет,
   и отказывается работать на устаревшем описании.
3. **Сверка с документацией** — команда, которая заново загружает разделы, сравнивает хеши и
   записывает расхождение в сам файл описания, чтобы локальный запуск без сети его видел.

Результат гейта — **перечень пробелов**: что из полей Claude Code, субагентов и hooks
Antigravity не воспроизводит. Перечень вычисляется из двух описаний, а не пишется руками,
поэтому его можно перепроверить.

## Решения по реализации

- **Формат данных — YAML.** Читается человеком в ревью (FR-10 требует именно чтения), уже есть
  в зависимостях проекта через frontmatter скиллов. JSON проиграл на читаемости диффа.
- **Раскладка** — `specs/<vendor>/<environment>-<version>.yaml`: `specs/anthropic/claude-code-2.1.yaml`,
  `specs/google/antigravity-2.0.yaml`. Папки `specs/anthropic/` и `specs/google/` уже есть в репозитории.
  Два описания одной среды не затирают друг друга, потому что версия — в имени файла (R08).
- **Нормализация текста раздела** (R34i) объявляется в описании полем `normalization: v1` и значит:
  берётся markdown-версия страницы (`<url>.md` — обе документации её отдают), из неё вырезается
  раздел от заголовка-якоря до следующего заголовка того же или высшего уровня. Якорь — это
  текст заголовка без решёток; сравнение после обрезки пробелов, схлопывания пробелов внутри
  и приведения регистра. Совпало несколько заголовков — ошибка, а не первый попавшийся.
  Затем NFC,
  `\r\n` → `\n`, обрезка хвостовых пробелов в строках, схлопывание пустых строк подряд в одну,
  обрезка пустых строк по краям. `sha256` от результата в UTF-8.
  *Почему так:* html-страница меняется от оформления, markdown — от содержания (R13).
- **Запись источника без `anchor` или без `sha256` — ошибка проверки схемы** (R04). Не «расхождение
  на потом»: файл описания с неподтверждённой записью не загружается вовсе, поэтому такая запись
  физически не может дожить до сравнения. Виды `Discrepancy` — `changed` и `unreachable`, оба
  появляются только из сверки.
- **Оценка поддержки** у записи — `supported` / `unsupported` / `unknown`. Это не словарь оценок
  переноса из §5 PRD: тот про свойства **переноса**, этот — про то, что написано в документации
  среды. Словарь §5 здесь не предвосхищается.
- **Свойство, которого нет в описании, — `unknown`** (R22). Отсутствие записи никогда не читается
  как «не поддерживает»: разница между «документация молчит» и «документация говорит нет» — ровно
  то, ради чего собираются источники.
- **Устаревание** (R17): `stale_after_days` объявляется в самом описании, по умолчанию 30.
  Устарело = `discrepancies` непусто **или** `today - checked_at > stale_after_days`.
  `is_stale()` — предикат; отказ даёт `select()`, поднимая `StaleSpec`. Обойти можно только
  явным `allow_stale=True` — он нужен ядру, чтобы воспроизвести прошлый перенос (FR-9),
  и сам по себе ничего не разрешает.
- **Сверка** (R12) — отдельный модуль, единственный в проекте, который ходит в сеть.
  Ошибка сети и код ответа не 200 — запись `unreachable` в `discrepancies`, не молчание (R14).
- **Перечень пробелов вычисляется** (R24): для каждой записи исходной среды ищется соответствие
  в целевой; исход — `reproduced` / `missing` / `unknown`. Руками пишется только вводный абзац.
  *Почему так:* написанный руками перечень невозможно перепроверить, а он — критерий продолжения проекта.
- **Пустой перечень — сигнал, а не успех** (R25): если `missing` и `unknown` пусты, команда
  возвращает ненулевой код и говорит, что продукт в текущем виде не нужен. Этот код — свойство
  команды разработчика, а не исход адаптера: таблица FR-27 его не касается и не расширяется.
- **Зависимости**: уже объявленные в проекте `pydantic>=2` (форма и проверка схемы описания),
  `pyyaml` (чтение файлов) и `urllib` из стандартной библиотеки (сверка). Новых не добавляется —
  CFP §4 уровень 3.

Схема описания среды (структура, не код):

```yaml
schema_version: 1
vendor: anthropic
environment: claude-code
version_range: ">=2.1.0,<2.2.0"
checked_at: 2026-09-14
stale_after_days: 30
normalization: v1
sources:
  - id: skills-frontmatter
    url: https://code.claude.com/docs/en/skills
    markdown_url: https://code.claude.com/docs/en/skills.md
    anchor: "Frontmatter fields"
    sha256: "…"
    checked_at: 2026-09-14
    environment_version: "2.1.270"
capabilities:
  - id: skill.frontmatter.allowed-tools
    kind: skill-field          # skill-field | subagent-field | hook-event | settings-file
    support: supported
    source_id: skills-frontmatter
    since_version: "2.1.246"   # необязательно; когда документация называет версию введения
    note: "ограничивает набор инструментов агента"
layout:                        # структура папок среды (PRD §2)
  - id: skills.root
    path: ".claude/skills/"
    source_id: skills-location
limits:
  - id: skill.file.size
    value: 15000
    unit: bytes
    source_id: skills-limits
tool_names:                    # только у целевой среды (R27)
  - from: Read
    to: read_file
    source_id: antigravity-tools
invisible_sources:             # только у исходной среды (R28)
  - id: user-level-hooks
    path: "~/.claude/settings.json"
    source_id: settings-precedence
discrepancies: []              # дописывается сверкой (R15)
```

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `envspec.normalize` | правилом нормализации и хешированием (R34i) | `section_text(markdown, anchor) -> str`, `normalize(text) -> str`, `digest(text) -> str` | разбор markdown, порядок шагов нормализации |
| `envspec.model` | формой описания среды | датаклассы `EnvSpec`, `Capability`, `Source`, `Limit`, `ToolName`, `Discrepancy`, перечисление `Support` | сериализацию YAML |
| `envspec.loader` | чтением, проверкой схемы, выбором по версии, устареванием | `load(path)`, `load_all(root)`, `select(root, vendor, environment, version)`, `is_stale(spec, today)`, `EnvSpec.capability(id) -> Support` | сравнение версий, поиск файлов |
| `envspec.gaps` | сравнением двух описаний | `compare(source, target) -> GapReport`, `render_markdown(report)`, `render_json(report)` | правило сопоставления записей |
| `envspec.freshness` | сверкой с документацией поставщика (единственный сетевой модуль) | `check(spec, fetch=…) -> list[Discrepancy]`, `record(path, discrepancies)` | HTTP, заголовки, повторы |

**Швы для тестов — два**, оба уже публичные:
`envspec.loader` (чтение → выбор → устаревание) и `envspec.normalize` (текст → хеш).
`freshness` тестируется через подставляемую функцию `fetch` — сеть в тестах не нужна.
`gaps` тестируется через `compare` на двух маленьких описаниях.

## Открытые места

Заглушек нет. Единственное место, где данные приходят извне, — содержимое описаний;
оно собирается из официальной документации в ходе сборки, а не подставляется.

Риск, который надо назвать вслух: документация Antigravity может молчать о субагентах,
hooks и правах. Тогда эти записи получают `unknown`, а не `unsupported`, и перечень
пробелов честно скажет «неизвестно» вместо «не поддерживает». Это результат, а не провал.

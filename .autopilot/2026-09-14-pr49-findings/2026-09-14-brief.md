## 🔴 Критическое — не мержить

> `src/agent_skill_adapter/convert.py:307` — an unhashable frontmatter key raises `TypeError`
> past every handler: traceback, no report, exit 1 instead of the documented 6.

> `key in seen` runs before `SafeConstructor.construct_mapping`, which is what raises
> `ConstructorError` ("found unhashable key") on this input — a `yaml.YAMLError` the handler
> at convert.py:393 would have turned into the documented structural refusal, exit code 6.
> Intercepting it first turns that refusal into an uncaught `TypeError`: a `SKILL.md` whose
> header carries `? [a, b]` / `: v` makes the command print a traceback, write nothing to
> standard output, and exit 1 — the code that tells a caller the transfer succeeded with
> known losses. Reproduced by running the command; FR-15 and FR-26 both fail on the same input.

> `src/agent_skill_adapter/convert.py:873` — only `ConvertError` is caught, so an `OSError`
> while reading or copying escapes: traceback, no report, exit 1, and a partially assembled
> tree left under `--out`.

> `_assemble` copies the parts one at a time at convert.py:682-689, after the collision and
> escape checks have passed. A dangling symlink inside a bundled directory makes
> `shutil.copytree` raise there, and the run then prints a traceback, emits no JSON report,
> exits 1 — again the code for a lossy transfer — and leaves a half-assembled tree under
> `--out`. That is the damage the comment at convert.py:649-653 promises not to do, and it
> breaks the rule that every outcome still produces a report. Reproduced with
> `scripts/dangling -> /nonexistent`: `SKILL.md` written, `scripts/` left empty, exit 1.
> `stat` and `read_bytes` on an unreadable `SKILL.md` fall through the same hole.

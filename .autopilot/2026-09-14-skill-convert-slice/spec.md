# Спецификация: решения §5 и узкий срез конвертера Claude Code → Antigravity

## Задача

Описания двух сред собраны, пробелы посчитаны: 26 записей воспроизводятся, 73 — `unknown`.
Но конвертера нет. Человек, у которого лежит папка скилла Claude Code и который хочет
пользоваться им в Antigravity, до сих пор не может ничего запустить и узнать два ответа:
перенесётся оно или нет, и что именно потеряется по дороге.

Мешает этому не объём работы, а нерешённое: PRD §5 держит десять решений «до готовности
описаний сред», и три из них решают, будет ли конвертер вообще что-то конвертировать.
Пока «неизвестное = отказ», конвертер откажет почти на каждом настоящем скилле — у любого
из них есть поле, про которое документация Antigravity молчит.

## Решение

Сначала записываются три решения §5 — словарь оценок, правило для `unknown`, обращение
с hooks. Потом появляется одна команда:

```
uv run agent-skill-adapter convert <папка-скилла> --out <куда>
```

Она читает папку скилла, спрашивает у описаний сред про каждое найденное свойство,
говорит вывод по файлу и код возврата, а с `--out` ещё и раскладывает скилл в то место,
которое описание Antigravity называет своим. Без `--out` ничего не пишется — только отчёт.

## Решения по реализации

**Словарь оценок — берётся существующий, а не изобретается.** `envspec.gaps.Outcome`
(`reproduced` / `missing` / `unknown` / `out-of-scope`) уже описывает оценку одного свойства
и уже покрыт тестами. Почему так: третий словарь для того же понятия — это перевод между
словарями в каждом модуле.

ADR-0006 записывает это решение и говорит вслух, что оно спорит с ADR-0003: тот отверг
«переиспользовать словарь переноса из PRD §5» на том основании, что `Support` описывает,
что задокументировал поставщик, а не как переносится свойство. Спора с этим нет —
`Support` остаётся при своём. Переиспользуется `Outcome`, а он и есть вывод сравнения
двух описаний: «воспроизводит ли цель эту запись» — ровно тот вопрос, который конвертер
задаёт про свойство скилла. Словарь §5 добавляет к нему то, чего в сравнении описаний
нет вовсе: вывод по файлу.

**Вывод по файлу** — `Verdict`: `clean` (всё воспроизводится), `lossy` (что-то теряется, но
перенос осмыслен), `undecidable` (сведений недостаточно). Четвёртого значения «перенос
запрещён» нет: в этом срезе ни одна строка таблицы сборки его не производит, а значение,
которого никто не выдаёт, — это ветка кода, которую никто никогда не проверит.
Появится вместе с FR-36, где запрет и определяется.

**Итог запуска — тот же `Verdict`**, худший из выводов файлов. Отдельного типа нет:
одно понятие, один словарь. Поэтому новое имя в §5 вводится ровно одно.

**Правило сборки — таблица, и она же правило для `unknown`.** Оценка свойства плюс origin
дают вывод по свойству; вывод по файлу — худший из выводов его свойств; итог запуска — худший
из выводов файлов. Порядок тяжести: `undecidable` > `lossy` > `clean` — он повторяет порядок остановок FR-27.

| оценка свойства | origin | вывод | код возврата |
|---|---|---|---|
| `reproduced` | любой | `clean` | 0 |
| `out-of-scope` | любой | `clean` | 0 |
| `missing` | любой | `lossy` | 1 |
| `unknown` | `extension` | `lossy` | 1 |
| `unknown` | `specification` | `undecidable` | 3 |

Та же таблица применяется к субагентам, и отдельного решения они не требуют: раскладка
`.claude/agents/*.md` → `.agents/agents/` и `~/.claude/agents/*.md` → `~/.gemini/config/agents/`
воспроизводится, 7 полей субагента из 19 — тоже, остальные 12 — расширения, значит потеря
с пометкой. Читать папки субагентов этот срез не умеет: вход — одна папка скилла (R07).
Решение §5 про субагентов снимается таблицей, реализация ждёт блока B.

Почему `missing` не запрещает перенос: целевая среда сказала прямо, что не поддерживает —
это известная потеря, а не нехватка сведений. Почему `unknown` по спецификации запрещает:
целевая среда объявила, что реализует этот формат, значит про его поле она обязана была
сказать, и её молчание — не наша неполнота, а её. NFR-3 при этом держится: разрешающий
итог (код 0) на неизвестном по-прежнему невозможен.

**Hooks — правится описание, а не конвертер (W1).** `hook.event.PreToolUse` у Claude Code
документирован словами «before a tool call executes; can block it» — это два разных
утверждения в одной записи. Разделяются: событие остаётся `hook.event.*`, способность
запретить становится записью `hook.decision.block` нового вида `hook-decision`. У Claude Code
она `supported` (документация говорит прямо), у Antigravity — `unknown` (страница
про поведение при ненулевом коде возврата молчит). Дальше работает правило origin, hooks —
расширение, значит потеря с пометкой. Особого правила про hooks в конвертере нет.
Почему так: вопрос «запрещать или выносить наружу» существовал только потому, что одна
запись описания отвечала за две разные вещи.

**Перенесённый hook честно помечается (W2).** Там, где целевая среда воспроизводит событие
(`PreToolUse`, `PostToolUse`, `Stop`), запись переносится, а в отчёт идёт строка о том, что
поведение при ненулевом коде возврата целевая среда не документирует. Молчание про запрет
не выдаётся за работающий запрет.

**Готовая запись hook кладётся отдельным файлом, а не вписывается в чужой.** Описание
Antigravity называет местом hooks `.agents/hooks.json` (запись `hooks.project`) — общий файл
рабочего пространства, в котором уже может лежать чужое. Слить своё с чужим — это FR-40,
столкновение с существующим результатом, и целый отдельный кусок работы. Поэтому срез пишет
`<out>/hooks.json` рядом с собранным скиллом, а отчёт называет путь назначения из описания
и говорит: впиши эту запись туда сам.

**Остальные три обхода идут в отчёт текстом, не кодом.** Для непереносимого hook отчёт
называет их по имени: перенести запрет в тело скилла (слабее на порядок — модель может
ослушаться), вынести проверку в pre-commit или шаг CI (годится только для проверок над
файлами: hook, запрещающий действие агента, git не видит), свернуть событие к ближайшему
поддерживаемому (сработает чаще оригинала — это уже правила перевода, FR-6). Конвертер
ничего из этого не делает: FR-22 запрещает ему разбирать содержимое команды, значит выбрать
между ними он не может, а человек может.

**«Claude to Gemini» в терминах описаний — это `anthropic/claude-code` → `google/antigravity`.**
Antigravity — среда Google, и её пользовательская раскладка лежит именно в `~/.gemini/`:
`~/.gemini/config/skills/`, `~/.gemini/config/agents/`, `~/.gemini/config/hooks.json`.
Одно и то же, названное с двух сторон: пользователь говорит «Gemini» про марку,
описание говорит «antigravity» про среду.

**Уровень раскладки выбирается флагом `--scope project|user`, по умолчанию `project`.**
Он решает, какая запись `layout` берётся: `skills.project` (`<workspace-root>/.agents/skills/`)
или `skills.user` (`~/.gemini/config/skills/`). Почему по умолчанию `project`: писать
в домашнюю папку без явного указания — это менять окружение человека мимоходом.

**Раскладка берётся из `layout`, в коде путей нет.** Целевой путь — `LayoutEntry.path`
записи `skills.project` описания Antigravity (`<workspace-root>/.agents/skills/`);
подстановки `<skill-name>` и `<workspace-root>` разворачиваются эмиттером. Почему так:
путь, вписанный в код, — это описание среды, спрятанное от сверки.

**Выход по умолчанию — отчёт, запись только по `--out`.** Без флага ничего не создаётся.
Почему так: чужую файловую систему не трогают без явного указания, и отдельный флаг
`--dry-run` тогда не нужен.

**Версии сред задаются явно (FR-4).** `--source vendor/environment@version`,
`--target …`; не заданы — код 3. Выбор описания — существующий `loader.select`.

**Отчёт.** Машиночитаемый JSON — в stdout либо в файл по `--report`; читаемый человеком —
в stderr. Выпускается при любом исходе, включая сбой чтения. Поля записи отчёта названы
здесь, потому что по «строке в отчёте» его не собрать:

```json
{
  "report_schema": 1,
  "outcome": "lossy",
  "exit_code": 1,
  "source": {"vendor": "anthropic", "environment": "claude-code", "version": "2.1.0"},
  "target": {"vendor": "google", "environment": "antigravity", "version": "2.0.0"},
  "skill": {"path": "skills/example", "name": "example"},
  "properties": [
    {"id": "skill.frontmatter.model", "found_as": "frontmatter key `model`",
     "outcome": "unknown", "origin": "extension", "verdict": "lossy",
     "source_says": "…", "target_says": "…", "note": null}
  ],
  "written": [{"from": "SKILL.md", "to": ".agents/skills/example/SKILL.md"}],
  "advice": ["…"]
}
```

`report_schema` первым полем — версия схемы отчёта (FR-24). `found_as` — где в папке скилла
свойство было замечено: ключ frontmatter, папка бандла, событие hook; по нему человек находит
место, не имея нашей таблицы id. `written` пуст без `--out`. `advice` — те самые обходы
текстом. Свойство, которого нет ни в одном описании, попадает сюда со своим `found_as`,
`outcome: "unknown"` и `origin: "extension"`: молча оно не пропадает.

**Один модуль, не пакет.** `src/agent_skill_adapter/convert.py`. `envspec/` — пакет, потому
что в нём шесть модулей; у среза одна сквозная функция и три шага. Разделение на пакет —
когда файл перевалит за три сотни строк.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `convert` | чтением папки скилла, оценкой, сборкой, отчётом | `convert(skill_dir, source, target, *, out=None) -> Conversion` | разбор frontmatter, отображение находок в id записей, подстановки в путях |
| `envspec.gaps` | сравнением описаний | `compare(source, target, bases) -> GapReport` (существует) | — |
| `envspec.loader` | выбором описания по версии | `select(...)`, `base_specs(...)` (существуют) | — |

Шов для тестов — **один**: `convert(...)`. Поведение проверяется через него на крошечных
описаниях и временной папке скилла, как это уже сделано в `test_envspec_gaps.py`.
Внутренние шаги отдельными тестами не покрываются: правило сборки видно на выходе `convert`.

## Открытые места

Заглушек, ждущих факта от пользователя, нет: всё нужное лежит в репозитории.

Одно следствие принятого правила стоит знать заранее: `skill.dir.references` и
`skill.dir.assets` — `unknown` по **спецификации**, значит скилл с папкой `references/`
или `assets/` получит код 3 и не перенесётся. Antigravity называет свои папки `examples/`
и `resources/` — сопоставить их могли бы правила перевода, но их в этом срезе нет.
Это не заглушка, а прямое следствие выбора «разделить по origin».

# PRD-001: Agent Skill Adapter

**Коротко.** Адаптер переносит настройки агента из Claude Code в Google Antigravity и показывает, что при переносе теряется. Работает без сети, на одних входных данных всегда даёт один результат. Для разработчиков скиллов и для CI. Первая версия: два описания сред, разбор всего непереносимого (hooks, субагенты, права), работа с текстом скилла, шаг для GitHub Actions. Девять решений сознательно отложены до готовности описаний сред — см. §9.

## 1. Проблема

Сам файл скилла переносится легко. Спецификация Agent Skills открыта (agentskills.io), папку `.agents/skills/` читают Codex, Cursor, Copilot, OpenHands, Gemini CLI и Antigravity, а `npx skills` уже раскладывает скиллы по 79 средам.

Сложность в другом. Спецификация требует всего два поля — `name` и `description`. Claude Code добавляет к ним восемнадцать своих: `hooks`, `context: fork`, `allowed-tools`, `model`, `effort`, `agent`, `arguments`, `disable-model-invocation` и прочие. Рядом лежат субагенты (`.claude/agents/*.md`) с их правами и лимитами (`permissionMode`, `maxTurns`, `isolation`, `mcpServers`) и hooks из `settings.json`.

Другой агент открывает такой скилл, молча пропускает незнакомые поля и запускается. Файл прочитан — поведение изменилось. Пропадают не украшения, а гарантии: скилл больше не работает в отдельном контексте, набор разрешённых инструментов агента не ограничен, проверки до и после вызова инструмента не выполняются, исчезает разделение на «запускает только человек» и «запускает только модель». Скилл с побочными эффектами — который умеет коммитить или деплоить — после такого переноса становится опаснее оригинала: теперь его может запустить модель сама.

В prgate-kit (наш набор скиллов) это уже стоит ручной работы. Скиллы написаны под Claude Code, под другие среды их переписывают вручную, и никто не может сказать, сохранилось ли поведение. Среды меняются быстрее, чем окупается ручная переделка: поля Claude Code привязаны к версиям — `background` работает с v2.1.218, `maxTurns` с v2.1.246.

## 2. Что мы делаем

Адаптер переносит настройки агента из одной среды в другую и честно показывает, что при этом теряется. Перенос идёт без сети и без обращения к языковым моделям: на одних и тех же входных данных всегда получается один и тот же результат.

Основа продукта — **описание среды**. Это машиночитаемый документ, составленный по официальной документации поставщика: что среда умеет, чего не умеет, какая у неё структура папок, какие поля она понимает и какие у неё пределы размера. У каждой записи указано, откуда сведения взяты: ссылка на документацию, дата проверки и версия среды. Описания сред появляются раньше кода переноса — это первый результат работы.

**Главная ценность — именно то, что спецификация не покрывает.** Общую часть, которую понимают все среды, переносить умеют и без нас. Адаптер берёт на себя остальное: hooks, субагентов, права и ограничения инструментов агента, текст скилла, связи между файлами. Каждый такой случай получает явный исход: перенесено с заменой, вынесено наружу отдельным механизмом или запрещено — с объяснением причины. Исход «запрещено» — тоже результат работы: есть гарантии, которые в чужой среде не воспроизводятся ничем, и честно сказать об этом лучше, чем выдать файл, который выглядит рабочим.

## 3. Термины

- **Оценка** — что стало с одним свойством при переносе.
- **Вывод по файлу** — что стало с одним файлом настроек; собирается из оценок его свойств.
- **Итог запуска** — что стало со всем переносом; собирается из выводов по файлам. Код возврата отражает итог запуска.
- **Инструмент агента** — то, чем пользуется агент: чтение файла, запуск команды, поиск. У сред они называются по-разному. Сам продукт в этом документе называется адаптером, чтобы слова не путались.

## 4. Для кого

- **Разработчик скиллов.** Переносит свой набор в другую среду и хочет знать цену переноса заранее, а не после поломки.
- **Автоматизация в CI.** Запускает перенос и проверку без человека, с настройками по умолчанию, получает машиночитаемый отчёт и код возврата.
- **Дежурный по актуальности.** Следит за тем, чтобы настройки оставались корректными для заявленных сред, когда меняются скиллы или обновляются сами среды. Ему нужен режим проверки без записи.

## 5. Чего мы не делаем

- **Не устанавливаем.** Разложить файлы по папкам сред умеет `npx skills`. Адаптер готовит результат в стандартном виде и отдаёт его этому установщику.
- **Не создаём новые скиллы.** Адаптер переносит существующие, не сочиняет.
- **Не проверяем поведение на живой модели.** Адаптер даёт предсказуемый ответ о переносе. Проверка «ведёт ли себя так же» — это отдельные прогоны на моделях, они стоят денег и запускаются отдельно, по желанию.

## 6. Границы первой версии

- Направление одно: Claude Code → Google Antigravity. Это первая поверхность Gemini, остальные — после.
- На вход подаётся репозиторий целиком. Отдельный скилл без репозитория пока не рассматриваем.
- Непереносимое входит в первую версию целиком: hooks, субагенты, права с ограничениями инструментов агента, а также текст скилла — названия инструментов внутри инструкций, разметка, ссылки, размер. Отложен способ обращения с каждым из них, а не их разбор (§9).

## 7. Функциональные требования

### A. Описания сред

Что среда умеет — данными, по официальной документации, с указанием источника и версии.

- **FR-1.** Описание среды хранится в файле данных, а не в коде. Правила переноса не зашиты внутрь программы.
- **FR-2.** У каждой записи о свойстве среды указан источник: ссылка на официальную документацию, дата проверки, версия среды.
- **FR-3.** Описание привязано к версии среды, и диапазон поддерживаемых версий указан явно.
- **FR-4.** Версии исходной и целевой среды задаются явно — флагом или файлом настроек — и записываются в отчёт. Версия среды не выводится из репозитория: это свойство машины, а не кода. Если версия не задана, берётся минимальная поддерживаемая; если она вне объявленных диапазонов, адаптер отказывает, а не берёт ближайшее описание.
- **FR-5.** Описания разных версий среды хранятся рядом, каждое со своей датой проверки. Новая версия не затирает предыдущую: перенос можно повторить на том описании, на котором он делался раньше. Если входным данным соответствует несколько описаний, действует правило выбора, объявленное в самих описаниях, а версию можно закрепить флагом.
- **FR-6.** Правила перевода версионируются отдельно от описаний сред. Чтобы повторить прошлый перенос, нужны обе: версия описаний и версия правил — они записываются в отчёт.
- **FR-7.** По расписанию в CI проверяется, изменилась ли документация поставщика: сравниваются версия и содержимое разделов, по которым составлялось описание. Значимым считается изменение этих разделов, а не оформления страницы. Недоступность источника — тоже расхождение, а не подтверждение актуальности.
- **FR-8.** Найденное расхождение записывается в сам файл описания и попадает в репозиторий. Признак устаревания не живёт только в журнале CI: локальный запуск без сети обязан его видеть.
- **FR-9.** На устаревшем описании адаптер не выдаёт разрешающий итог — он сообщает, что сведений недостаточно, отдельным кодом возврата. Уже выполненный перенос это не отменяет: закреплённая версия описания продолжает работать, пока её не сняли (FR-5).
- **FR-10.** Описание среды составляет языковая модель по официальной документации и открывает пулл-реквест с новой версией. В основную ветку изменения попадают только после чтения человеком: модель пишет черновик, решение принимает ревьюер. Старая версия остаётся на месте и годится для работы.
- **FR-11.** В первую версию входят два описания: Claude Code как источник и Google Antigravity как цель.
- **FR-12.** Свойство, которого нет в описании, считается неизвестным, а не поддерживаемым. Свойство, которое в описании есть, но правила перевода для него нет, тоже считается неизвестным.

### B. Чтение исходных настроек

Репозиторий читается целиком и безопасно: адаптер работает с чужим кодом.

- **FR-13.** На вход подаётся репозиторий. Читаются все виды файлов настроек, которые в нём найдены.
- **FR-14.** Чтение не выходит за корень поданного репозитория. Символические ссылки наружу не разыменовываются, а попадают в отчёт.
- **FR-15.** В заголовке файла (frontmatter) принимается только YAML, без якорей и алиасов, в кодировке UTF-8, с пределами на размер и глубину. Исполняемые вставки отвергаются: адаптер читает чужие репозитории и не должен запускать их содержимое.
- **FR-16.** Структурная поломка файла — не читается, нет обязательных полей, определение скилла встречается дважды в разных папках — прерывает работу на этапе чтения с объяснением, что именно не так и где. Неизвестное поле работу не прерывает: оно получает оценку «неизвестно» и запрещает разрешающий итог.
- **FR-17.** Настройки, которые лежат вне репозитория — например, hooks уровня пользователя, — адаптер не видит. Отчёт перечисляет такие источники как заведомо невидимые, чтобы обещание «ничто не пропадает молча» не оказалось ложным.
- **FR-18.** Если файлов настроек не найдено ни одного, это отдельный исход со своим кодом возврата, а не успешный перенос.
- **FR-19.** Внутреннее представление сохраняет связи между файлами: какой скилл опирается на какой hook, какого субагента, какой инструмент агента или файл. Обход связей защищён от зацикливания, битая связь получает оценку «неизвестно».

### C. Разбор переноса и отчёт

Каждое свойство получает оценку, каждый файл — вывод, запуск — итог; всё это попадает в отчёт.

- **FR-20.** Каждое свойство исходной настройки получает оценку относительно целевой среды.
- **FR-21.** Hooks, субагенты и права с ограничениями инструментов агента оцениваются в первой версии наравне с остальным. Ни один из этих классов не пропускается молча, даже если целевая среда его не поддерживает.
- **FR-22.** У hook оценивается точка подключения: событие, условие срабатывания, блокирует ли он действие. Содержимое команды адаптер не разбирает и не исполняет — это записано в отчёте как граница оценки.
- **FR-23.** Каждый файл получает свой вывод, собранный из оценок его свойств; весь запуск получает итог, собранный из выводов по файлам. Правило сборки описано таблицей и покрывает все случаи, включая пустой набор и смесь разных выводов.
- **FR-24.** Отчёт содержит: итог запуска, выводы по файлам, оценки свойств, соответствие «было в источнике → стало в цели» со ссылкой на место в исходном файле, версии сред, описаний и правил перевода, и объяснение, что делать дальше.
- **FR-25.** Значения полей, похожие на секреты, в отчёт не попадают: вместо значения указывается место. Отчёт публикуется в логах сборки и в комментариях к пулл-реквестам — он не должен становиться каналом утечки.
- **FR-26.** Отчёт выпускается в двух видах: читаемом человеком и машиночитаемом. Они идут разными потоками и не смешиваются. Машиночитаемый отчёт выпускается при любом исходе, включая сбой чтения.
- **FR-27.** Работа завершается кодом возврата. У каждого исхода свой код: перенос без потерь, перенос с потерями, запрет на перенос, сведений недостаточно, отмена человеком, файлов настроек не найдено, не смогли прочитать исходные настройки, сборка не прошла проверку. Коды перечислены и не меняются от версии к версии.
- **FR-28.** Разбор выполняется без сети и без обращений к языковым моделям.
- **FR-29.** Повторный запуск на тех же входных данных, том же описании и той же версии правил даёт точно такой же результат, до байта. Для этого: пути в отчёте только относительные от корня репозитория, обход файлов и сортировка ключей детерминированы, имена нормализованы одинаково на всех системах, переводы строк приведены к одному виду. Поля, которые меняются от запуска к запуску — время, версия адаптера, пути машины, — перечислены и в сверку с эталоном не входят.

### D. Текст скилла

Переносится не только заголовок: инструкции внутри скилла тоже привязаны к среде.

- **FR-30.** Названия инструментов агента внутри инструкций переписываются под целевую среду по таблице соответствий из её описания. Инструмент, которому в целевой среде соответствия нет, попадает в отчёт и не заменяется похожим по смыслу.
- **FR-31.** Разметка приводится к виду, который целевая среда понимает. Конструкции, характерные для исходной среды и бессмысленные в целевой, не переносятся молча.
- **FR-32.** Предел размера — свойство среды и записывается в её описание наравне с остальными. У каждой среды он свой: предел на файл скилла, на список скиллов, на общий объём.
- **FR-33.** Скилл, не влезающий в предел целевой среды, разбивается: основной файл остаётся кратким, подробности выносятся в отдельные файлы рядом. Что именно выносится — решает описание среды, а не догадка.
- **FR-34.** После переноса и разбиения все ссылки между файлами ведут туда, куда должны. Висячая ссылка — причина не записывать результат.

### E. Сборка под целевую среду

Результат проверяется до записи, пишется атомарно и только внутрь выходной папки.

- **FR-35.** Пока итог не подтверждён, файлы не пишутся. Подтверждает человек вручную либо, в неинтерактивном запуске, заранее заданная настройка. Если подтверждения нет и настройка не задана — отказ без записи, а не ожидание ввода.
- **FR-36.** Если итог запрещает перенос, не создаётся ни одного файла.
- **FR-37.** Собранный результат проверяется до записи: соответствует формату целевой среды, не содержит следов исходного формата, имена не сталкиваются друг с другом и допустимы в целевой среде. Не прошло проверку — не пишем, и это отдельный исход, не путающийся с запретом на перенос.
- **FR-38.** Запись идёт только внутрь выходной папки. По ссылкам, ведущим за её пределы, адаптер не пишет.
- **FR-39.** Запись атомарная: либо появляется весь результат, либо ничего. Временные файлы лежат на том же томе и убираются при следующем запуске.
- **FR-40.** Результат адаптера порождается заново при каждом запуске и ручной правке не подлежит: это записано в самих файлах. При столкновении с существующим результатом по умолчанию отказ; перезапись включается флагом. Файлы, которых больше нет в источнике, перечисляются в отчёте как осиротевшие.
- **FR-41.** Способ обращения с непереносимыми свойствами задаёт человек — файлом настроек или флагом команды; флаг перекрывает файл. Неизвестное значение — отказ, а не молчаливое умолчание. В неинтерактивном запуске берётся значение по умолчанию.
- **FR-42.** Всё, что при переносе упростилось или лишилось гарантии, записывается в отчёт. Тихо ухудшать поведение адаптер не имеет права — ради этого он и делается.
- **FR-43.** Результат складывается в стандартный вид, пригодный для установки внешним инструментом. Формат этого вида назван и версионирован наравне с описаниями сред, и его изменения отслеживаются так же (FR-7).

### F. Запуск в CI и версии

Первая внешняя точка — шаг для GitHub Actions; ядро при этом библиотека.

- **FR-44.** Поставляется готовый шаг для GitHub Actions: запускает проверку, публикует машиночитаемый отчёт, возвращает код возврата.
- **FR-45.** Есть режим проверки без записи: адаптер читает, разбирает, выдаёт отчёт и код возврата, но не создаёт ни одного файла. Это рабочий режим для CI и для наблюдения за актуальностью.
- **FR-46.** Ядро реализовано библиотекой; команда в терминале и шаг для CI — тонкие оболочки над ней. До первой стабильной версии набор функций библиотеки считается внутренним: пользоваться можно, совместимость не обещаем. Формат машиночитаемого отчёта стабилизируется раньше библиотеки — на нём стоят чужие проверки.
- **FR-47.** Если адаптер начинает запрещать то, что раньше разрешал, это ломает чужие сборки на неизменном коде. Такое изменение выпускается сменой крупной версии, с предупреждением заранее. Обратное — снятие запрета — объявляется в отчёте и примечаниях к выпуску: человек должен узнать, что прежнее решение можно пересмотреть.

## 8. Нефункциональные требования

- **NFR-1. Предсказуемость.** Одни и те же входные данные дают один и тот же результат. Проверяется сравнением с эталонными файлами, а не обещанием в документации.
- **NFR-2. Работа без сети.** Перенос и разбор проходят без сети, всегда. Сеть и языковая модель нужны только там, где готовятся описания сред: это отдельная задача, она идёт в CI заранее и в переносе не участвует.
- **NFR-3. Скорость.** Репозиторий до 200 файлов настроек обрабатывается не дольше пяти секунд. Для большего объёма предел задаётся явно, и превышение — отказ с объяснением, а не молчаливое ожидание.
- **NFR-4. При сомнении — отказ.** Неизвестное считается небезопасным. Нехватка сведений никогда не даёт разрешающего итога. Это поведение проверяется тестами наравне с обычным: на устаревшем описании, на неизвестном свойстве, на битом исходнике адаптер обязан отказать и ничего не записать.
- **NFR-5. Безопасное чтение.** Адаптер читает чужие репозитории: ничего из их содержимого не исполняется, чтение не выходит за корень, секреты не попадают в отчёт.
- **NFR-6. Дешёвое расширение.** Добавить новую среду — значит написать её описание, а не править ядро программы.

## 9. Решения, отложенные до готовности описаний сред

Принимаем их после того, как официальные спецификации собраны и начата сверка. Сейчас любое решение здесь было бы догадкой. Словарь оценок и выводов фиксируется первым — раньше, чем мы объявим стабильными формат отчёта и коды возврата.

- Какие бывают оценки свойств и выводы по файлам, как они называются.
- Что делать со скиллами, которые опираются на hooks: запрещать перенос или выносить проверку наружу, в git-hook или шаг CI.
- Как поступать с субагентами и правами, которые целевая среда понимает иначе или не понимает вовсе.
- Какие есть способы обращения с непереносимым и какой из них по умолчанию.
- Нужна ли числовая оценка совместимости и как её считать.
- Подстановки в тексте скилла (`$ARGUMENTS` и подобное), которым в целевой среде нет соответствия: оставлять с пометкой в отчёте или разворачивать в текст.
- Полный список видов файлов настроек, участвующих в переносе.
- Правило выбора описания, когда входным данным подходит несколько версий.
- Порог, после которого расхождение в документации считается значимым.

## 10. Риски

- **Описания устаревают.** Среды меняются быстрее, чем мы успеваем их описывать. Устаревшее описание опаснее отсутствующего: оно даёт ложное «всё в порядке». Что делаем: держим описания всех версий рядом с датами проверки, сверяем документацию по расписанию, помечаем расхождения в самих файлах, обновление приходит пулл-реквестом (FR-2, FR-5, FR-7, FR-8, FR-9, FR-10).
- **Описания дорого поддерживать.** Каждое обновление среды требует внимания. Что делаем: черновик пишет языковая модель и открывает пулл-реквест, человеку остаётся ревью. Выдумать поле трудно — черновик составляется сопоставлением с официальной спецификацией. Остаются пропуск поля, неверный статус поддержки и опора на устаревшую страницу; их ловит обязательное ревью, а ссылка на источник в каждой записи даёт ревьюеру чем сверять (FR-2, FR-10).
- **Среды становятся похожими.** Чем ближе они сходятся к общей спецификации, тем меньше разница, которую мы фиксируем. Что делаем: принимаем осознанно — это инструмент с конечным сроком пользы, а не платформа.
- **Нишу закроют сверху.** У тех, кто занимается установкой скиллов, есть аудитория, список сред и пути установки; добавить туда проверку совместимости — вопрос одного релиза. Что делаем: держим глубину, в которую им лезть незачем — непереносимые свойства, текст скилла и связи между файлами (FR-21, FR-30).
- **Ложная уверенность.** Разрешающий итог не означает, что поведение совпало. Что делаем: разделяем ответственность — разбор отвечает за перенос настроек, проверка поведения живёт отдельно и запускается сознательно.

## 11. Как поймём, что получилось

Базовый уровень снимается на prgate-kit при первом полном прогоне; пороги ниже — цель первой версии.

- Доля скиллов, перенесённых без ручной правки: не меньше 80% набора prgate-kit.
- Время от «хочу работать в новой среде» до работающего набора: меньше рабочего дня против нынешних недель ручной переделки.
- Доля потерь, обнаруженных отчётом, а не постфактум в работе: не меньше 95%.
- Возраст самого старого описания среды относительно текущей версии: не больше одной вышедшей версии среды.

Тревожные признаки, за которыми тоже следим: как часто человек отменяет итог адаптера как неверный, и сколько переносов прошло проверку, но сломалось в реальной работе.

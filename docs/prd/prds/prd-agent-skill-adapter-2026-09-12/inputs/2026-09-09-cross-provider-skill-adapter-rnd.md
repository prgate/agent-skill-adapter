# R&D: Кросс-провайдерный адаптер агентских скиллов (Cross-Provider Skill Adapter)

**Версия:** 0.0.5
**Дата:** 2026-09-10
**Статус:** R&D / Архитектурная спецификация (добавлены AI-First Repository Blueprint и гайд по организации нового репозитория)
**Область:** Адаптация и миграция скиллов, инструкций, правил и команд между средами Claude (Anthropic) и Gemini (Google / Antigravity), с расширением на Codex/Cursor.

---

## 1. Контекст и постановка проблемы

### 1.1. Текущий ландшафт
В индустрии ИИ-агентов для разработки сложилась фрагментация экосистем:
* **Anthropic / Claude Code:** Сформировал стандарт де-факто для агентских скиллов (спецификация Anthropic Agent Skills: папка `skills/<name>/SKILL.md`, YAML frontmatter, `scripts/`, `references/`, команды `commands/*.md`, агенты `agents/*.md`, правила `CLAUDE.md`). Огромная база готовых скиллов создана именно под этот стек.
* **Google / Gemini (Antigravity):** Обладает развитой системой кастомизации (Antigravity Customization System: проектные `.agents/`, правила `GEMINI.md` и `AGENTS.md`, прогрессивная подгрузка контекста, богатый инструментарий `replace_file_content`, `run_command`, реактивные сабагенты `invoke_subagent`).
* **OpenAI / Codex / Cursor:** Использует спецификации `.cursor/rules/*.mdc`, `.github/copilot-instructions.md`, системные файлы `AGENTS.md`.

### 1.2. Проблема
Разработчики вынуждены либо вручную переписывать скиллы под каждого провайдера, либо поддерживать несколько параллельных копий одного и того же поведения. Это ведёт к рассинхронизации логики, ошибкам рантайма и высокому барьеру миграции.

### 1.3. Принятое архитектурное решение
Попытка создать «абстрактный универсальный мета-стандарт с нуля» нецелесообразна и ресурсозатратна.
**Решение:** Считать формат **Claude Code базовым источником правды (Source of Truth)**, а адаптер строить как **контрактный компилятор-транслятор (Spec-Driven Migration Engine)**, преобразующий ассеты Claude в нативные форматы целевых сред (в первую очередь Gemini/Antigravity).

## 2. Базовые принципы ядра (Core Principles)

1. **Contract-First & Spec Conformance:**
   Никаких действий не предпринимается без валидации входных данных по официальной спецификации исходного провайдера (Anthropic) и выходных данных по спеке целевого провайдера (Google Gemini).
2. **Capability-Based Mapping (Модель возможностей):**
   Скилл рассматривается не как сырой текст, а как *исполняемый когнитивный рабочий процесс*, требующий конкретных возможностей рантайма (файловые операции, shell, запуск сабагентов, интерактивный ввод).
3. **Transparency & Feasibility Gate:**
   Перед физической записью файлов на диск генерируется **Отчёт о совместимости (Feasibility Report)** с явным вердиктом (`COMPATIBLE`, `COMPATIBLE_WITH_DEGRADATION`, `INCOMPATIBLE`). Любая скрытая деградация исключена.
4. **Fail-Closed Safety:**
   Если скилл требует критическую возможность, отсутствующую в целевом провайдере, трансформация блокируется с кодом возврата ошибки и диагностикой.
5. **Двухуровневый движок трансформации (Hybrid Engine):**
   * *Fast Deterministic AST (по умолчанию):* мгновенный, офлайн, без затрат токенов, детерминированный для 90%+ сценариев.
   * *Smart LLM Polish (опционально по флагу `--smart`):* вызов легкой модели (Gemini Flash) для перефразирования сложной прозы, описывающей внутренности инструментов.

## 4. Модель возможностей и матрица трансляции

### 4.1. Примитивы инструментов (Tool Vocabulary)

| Возможность | Claude Code (Source) | Gemini / Antigravity (Target) | Тип маппинга |
| :--- | :--- | :--- | :--- |
| **Shell Execution** | `Bash(command=...)` | `run_command(CommandLine=...)` | `EXACT` |
| **File Replacement** | `FileEdit(path, old_str, new_str)` | `replace_file_content(TargetFile, StartLine, EndLine, ...)` | `ADAPTED` (требует явных границ) |
| **File Reading** | `FileRead(path, offset, limit)` | `view_file(AbsolutePath, StartLine, EndLine)` | `ADAPTED` |
| **File Writing** | `FileWrite(path, content)` | `write_to_file(TargetFile, CodeContent)` | `EXACT` |
| **Directory Search** | `GlobTool(pattern)` / `LS` | `find_by_name(Pattern)` / `list_dir` | `EXACT` |
| **Content Search** | `GrepTool(pattern)` | `grep_search(Query, SearchPath)` | `EXACT` |
| **Subagent Spawn** | `Agent(prompt=...)` | `invoke_subagent(Subagents=[...])` | `ADAPTED` |
| **Subagent Define** | Отдельный markdown файл роли | `define_subagent` / dynamic prompt | `ADAPTED` |

### 4.2. Нормализация диалекта и разметки
* **XML-блоки:** `<rules>...</rules>` преобразуются в секции `## Rules` или GitHub-style alerts `> [!IMPORTANT]`.
* **Шаги выполнения:** `<step n="...">` транслируются в нумерованные списки Markdown.
* **Контекст и ссылки:** `<context>` разворачивается в секции `## Context`.
* **Теги размышления:** `<thinking>`, `<scratchpad>` удаляются или адаптируются под внутренние инструкции.

### 4.3. Адаптация команд, ролей и правил
* **Команды (`commands/*.md` с `$ARGUMENTS`):** компилируются в специализированные параметризованные скиллы (`skills/<command-name>/SKILL.md`) с регистрацией триггеров или в шаблоны рабочих процессов (workflows).
* **Роли сабагентов (`agents/*.md`):** транслируются в системные промпты сабагентов, пригодные для `define_subagent` и передачи через `invoke_subagent`.
* **Правила репозитория (`CLAUDE.md`):** генерируют `GEMINI.md` и/или синхронизируются с нейтральным `AGENTS.md`.

## 5. Спецификация отчёта о совместимости (Feasibility Report)

Отчёт строится на этапе 3 и выводится в терминал, а также сохраняется как артефакт `feasibility_report.md` (или JSON для машинной обработки).

### 5.1. Классификация вердиктов

* **`COMPATIBLE`:** 100% возможностей поддержаны. Потерь логики нет. Трансформация разрешена автоматически.
* **`COMPATIBLE_WITH_DEGRADATION`:** Скилл работоспособен, но часть вспомогательных функций модифицирована (например, интерактивный диалог переведён в неинтерактивный режим). Требуется явное подтверждение человека (`[Y/n]`) или флаг `--allow-degraded`.
* **`INCOMPATIBLE`:** Скилл опирается на возможности, принципиально недоступные в целевой среде. Трансформация блокируется.

### 5.2. Структура отчёта
1. **Header:** Исходный скилл, целевой провайдер, версия спеки, итоговый вердикт и оценка совместимости (score 0–100).
2. **Capability Matrix:** Таблица соответствия требуемых возможностей и статусов (`EXACT`, `ADAPTED`, `DEGRADED`, `BLOCKED`).
3. **Semantic Mapping Ledger:** Построчный список обнаруженных замен (номер строки, исходный примитив, целевой примитив).
4. **Actionable Diagnostics:** Предупреждения, советы по ручной доработке и рекомендации по включению `--smart`.

## 7. Интеграция с `prgate-kit`

В текущем репозитории `prgate-kit` уже реализована мультиязычная доставка ассетов (`scripts/kit_install.py`, `Makefile`).
Адаптер встраивается в цепочку сборки:

1. **Исходный код кита:** Все скиллы, команды и агенты оформляются в соответствии с конвенциями Claude Code (как принято в сообществе).
2. **Установка для Gemini (`make install AGENT=gemini`):**
   * Вместо прямого `rsync` `kit_install.py` вызывает `agent_skill_adapter.plan` $\to$ `agent_skill_adapter.convert`.
   * Перед установкой проверяется Feasibility Report.
   * В `~/.gemini/config/skills/` попадают нативно адаптированные артефакты.
3. **CI-гейт:** Добавляется проверка `make check-adapter`, гарантирующая, что все скиллы репозитория остаются на 100% совместимыми с Gemini (`COMPATIBLE`).

## 10. Killer Feature: Концепция «Babel для агентских скиллов»

### 10.1. Историческая аналогия с миром JavaScript
В 2015 году веб-разработка столкнулась с кризисом фрагментации: появился современный стандарт ECMAScript 6 (стрелочные функции, классы, модули), но браузеры пользователей не умели его исполнять. Если бы разработчики писали код под каждый браузер отдельно или ждали, пока все вендоры договорятся, веб-индустрия остановилась бы в развитии.

Решением стал **Babel**:
1. Разработчик пишет код **на самом выразительном современном диалекте** (ES6+).
2. Babel строит AST (абстрактное синтаксическое дерево).
3. Применяет плагины трансформации и **полифилы (polyfills)** для сред, где нет нужных нативных возможностей.
4. Выдаёт гарантированно работающий код под целевой рантайм.

### 10.2. Прорыв адаптера: «Write for Claude, Run Everywhere»
В агентной среде 2026 года формат **Claude Code стал современным ES6**:
* Сообщество пишет тысячи скиллов под синтаксис Клода (YAML frontmatter, XML-блоки, вызовы `FileEdit`/`Bash`, роли сабагентов).
* Другие рантаймы (Gemini / Antigravity, OpenAI Codex, Cursor) — это «разные браузеры» со своими встроенными API, ограничениями и форматами контекста.

Наш адаптер — это **Babel для агентских скиллов**. Он закрывает свободную рыночную нишу:
1. **Developer Experience (DX):** Инженеру не нужно учить формат Google Antigravity или Cursor MDC, чтобы создать скилл. Он пишет в общепринятом стандарте Claude Code.
2. **Семантический Lowering инструментов:** Адаптер не просто меняет слово `FileEdit` на `replace_file_content`. Он знает, что у Клода замена строковая (`old_str`), а у Gemini — позиционная (`StartLine`, `EndLine`), и адаптирует саму инструкцию, предотвращая галлюцинации модели.
3. **Agent Capability Polyfilling:** Если целевой рантайм не поддерживает сложную интерактивную конструкцию (например, субпроцесс опроса пользователя), адаптер внедряет безопасный полифил (статический шаг вывода или дефолтный выбор), явно фиксируя это в отчёте.

### 10.3. Три киллер-фичи, которых нет ни у одного инструмента на рынке

1. **Feasibility Gate & Explainability (Отчёт до действия):**
   Ни один инструмент в мире не говорит разработчику заранее: *«Этот скилл на 88% совместим с Gemini. Вызов bash сработает штатно, но интерактивный вопрос будет упрощён. Разрешить миграцию? [Y/n]»*. Это исключает появление «скиллов-зомби», ломающих прод-сессии.
2. **Spec-Driven Двойная Верификация:**
   Проверка входного скилла по официальной спецификации Anthropic и проверка результата по официальной спецификации Google Gemini. Если скилл кривой на входе — он отсекается до компиляции.
3. **Бесшовная интеграция в репозитории (Zero Runtime Overhead):**
   В репозитории хранится чистый, читаемый оригинал. Адаптер компилирует его на этапе сборки/установки (`make install` или CI). Никаких тяжелых прокси в рантайме.

## 11. Методология верификации и доказательство работоспособности (Proof of Correctness)

Главный вызов любого адаптера для LLM — это **доказательство эквивалентности (Equivalence Proof)**.
В традиционном компиляторе достаточно проверить байт-код или детерминированный вывод. В среде ИИ-агентов скилл управляет недетерминированной когнитивной моделью, поэтому доказательство должно охватывать не только синтаксис, но и практическое поведение агента в среде.

### 11.1. Пирамида верификации (4 уровня доказательства)

```
                       ▲
                      / \
                     /   \     УРОВЕНЬ 4: End-to-End Sandbox Execution
                    /  4  \    (Реальное исполнение задач в песочнице)
                   /───────\
                  /         \   УРОВЕНЬ 3: Dual-Harness A/B Eval
                 /     3     \  (Сравнение триггеринга и качества Claude vs Gemini)
                /─────────────\
               /               \  УРОВЕНЬ 2: Invariant & Target Spec Linters
              /        2        \ (Проверка схем, отсутствие утечек токенов, ссылки)
             /───────────────────\
            /          1          \ УРОВЕНЬ 1: Golden Master AST Snapshots
           /───────────────────────\ (Детерминированное сравнение деревьев разбора)
```

#### Уровень 1: Golden Master AST Snapshots (Детерминированный фундамент)
* **Как работает:** Набор эталонных Claude-скиллов (`fixtures/input/`) прогоняется через адаптер. Полученный результат сравнивается с заранее проверенным человеком золотым эталоном (`fixtures/golden/`).
* **Что доказывает:** 100% повторяемость, отсутствие регрессий в AST-трансформациях при рефакторинге адаптера. Тест выполняется за миллисекунды в обычном `pytest` без вызовов LLM.

#### Уровень 2: Invariant & Target Spec Linters (Контрактные проверки)
* **Target Spec Validator:** Прогон сгенерированных файлов через валидатор официальной схемы Google Antigravity / Gemini (проверка структуры каталогов, frontmatter, прав доступа).
* **Leak Detector (Отрицательные тесты):** Регулярные выражения и AST-сканеры проверяют, что в скомпилированном коде нет запрещенных артефактов Клода:
  * Не осталось слов `FileEdit`, `GlobTool`, `GrepTool`.
  * Не осталось нераспарсенных XML-тегов `<rules>`, `<thinking>`, `<guidelines>`.
  * Не осталось переменных подстановки `$ARGUMENTS`.
* **Link Integrity Check:** Автоматический обход всех Markdown-ссылок (`./scripts/*`, `../patterns/*`) с проверкой их физического существования в целевом окружении.

#### Уровень 3: Dual-Harness A/B Eval (Семантический поведенческий пруф)
Это главный эксперимент, доказывающий, что модель понимает адаптированный скилл так же, как оригинальный.
* **Схема эксперимента:**
  1. Берется контрольный датасет из $N$ тестовых сценариев (например, 20 реальных задач на ревью кода).
  2. Запускается **Оригинальный контур:** Модель Claude 3.5/3.7 исполняет исходный скилл в Claude Code harness.
  3. Запускается **Адаптированный контур:** Модель Gemini 2.0/3.0 исполняет адаптированный скилл в Antigravity harness.
  4. Сравниваются 4 объективные метрики (см. таблицу ниже).

#### Уровень 4: End-to-End Sandbox Execution (Живое выполнение в песочнице)
* В изолированном Docker-контейнере или временном git worktree агент Gemini получает реальный пользовательский запрос.
* Проверяется:
  * Агент выполняет цепочку шагов без сбоев (`tool call errors == 0`).
  * Не возникает зацикливания или преждевременной остановки.
  * Результирующий артефакт (например, коммит или ревью) соответствует Definition of Done.

### 11.2. Метрики и Definition of Proof (Критерии готовности)

| Метрика | Как измеряется | Целевой порог (Threshold) | Что означает при провале |
| :--- | :--- | :--- | :--- |
| **Trigger Concordance** | Процент совпадения активации скилла на контрольных промптах (Claude vs Gemini) | **$\ge 95\%$** | Описание (`description`) адаптировано плохо; Gemini не понимает, когда включать скилл. |
| **Tool Execution Error Rate** | Процент ошибок рантайма при вызове инструментов (`replace_file_content` line error, etc.) | **$0.0\%$** | Ошибка трансляции сигнатуры инструмента (например, перепутаны `StartLine` и строки). |
| **Step Completion Rate** | Доля шагов алгоритма скилла, пройденных агентом до финала | **$\ge 90\%$** | Инструкции сформулированы двусмысленно; агент сбивается с процедуры. |
| **Finding / Verdict Overlap** | Сходство найденных проблем при ревью одинакового диффа | **$\ge 85\%$** | Когнитивный дрейф: модель потеряла фокус или правила проверки. |

### 11.3. Эталонный сценарий доказательства на базе `prgate-kit`

В текущем репозитории `prgate-kit` уже есть развитая тестовая инфраструктура. Мы можем использовать её в качестве готового полигона:

1. **Тестовый объект:** Скилл `skills/pr-review/SKILL.md` (сложный многофазный скилл со ссылками на паттерны, скрипты и зависимости `pr-publish`, `pr-conventions`).
2. **Шаг 1:** Запуск `agent-skill-adapter convert skills/pr-review --target gemini`.
3. **Шаг 2 (Статика):** Прогон `test_install_flow.py` на сгенерированных файлах для агента `gemini` (проверка структуры каталогов и схемы).
4. **Шаг 3 (Eval):** Запуск готовых кейсов из `evals/pr-review/cases/` (например, `idempotency`, `clean-pr`, `migration-lock`) через Gemini API с адаптированным скиллом.
5. **Верификация:** Если Gemini находит те же критические дефекты (`findings`), что и Claude на исходном скилле — работоспособность и эквивалентность адаптера считаются **математически и эмпирически доказанными**.

### 11.4. Стресс-тестирование гейта на отказ (Chaos & Adversarial Testing)

Чтобы доказать надежность `Feasibility Gate`, тестируется не только успешная конвертация («happy path»), но и способность адаптера **отклонять несовместимые или вредоносные скиллы**:
1. **Тест на недоступные возможности:** Скилл требует вызова специфичного API Anthropic или недекларированного MCP-сервера $\to$ адаптер обязан вернуть `INCOMPATIBLE` и ненулевой код возврата, не создавая файлов на диске.
2. **Тест на битый синтаксис:** Скилл с незакрытыми XML-тегами, поврежденным YAML frontmatter или циклическими ссылками в `references/` $\to$ адаптер обязан упасть на этапе Source Spec Validation с понятной диагностикой.
3. **Тест на конфликт сигнатур:** Скилл явно требует поиска по `old_str` без номеров строк при целевом инструменте `replace_file_content` $\to$ адаптер обязан предупредить о деградации и потребовать подтверждения пользователя.

## 13. Контрактная модель и тройное версионирование (Tri-Partite Architecture)

Попытка напрямую связать два провайдера без формализации промежуточных контрактов неизбежно ведёт к хрупкой спагетти-логике при первом же обновлении любой из платформ. Чтобы архитектура была масштабируемой и устойчивой к изменениям вендоров, система организуется вокруг **трёх независимых версионируемых спецификаций** и **Translation Bus API**.

### 13.1. Трёхслойная природа спецификации провайдера ($S_A$ и $S_B$)

Спецификация среды ИИ-агента ($S_A$ для Claude, $S_B$ для Gemini) состоит из трёх ортогональных слоёв:
1. **Синтаксис и топология (Syntax & Topology):**
   * Схема YAML frontmatter (`name`, `description`, `dependencies`).
   * Иерархия каталогов (`SKILL.md`, `scripts/`, `references/`).
   * Диалект разметки (XML-теги vs Markdown-секции).
2. **Инструментальные примитивы (Tool Primitives):**
   * Сигнатуры системных тулов (`FileEdit(path, old_str, new_str)` vs `replace_file_content(path, start, end, ...)`).
   * Семантика модификации файлов (строковое вхождение без номеров строк vs позиционные диапазоны строк).
3. **Когнитивный профиль и среда (Runtime & Environment):**
   * Стратегия загрузки контекста (progressive disclosure vs полная инъекция).
   * Модель сабагентов (синхронный подпроцесс vs реактивный диспетчер `invoke_subagent`).
   * Политики безопасности и подтверждений (CFP-уровни трения vs интерактивный `Bash`-промптинг).

Каждая спека существует автономно и живёт по своему релизному циклу, задаваемому вендором: `anthropic.agent-skills@1.0.0`, `google.antigravity@2.1.0`.

---

### 13.2. Математическая необходимость тройного версионирования

Версия адаптера не может быть привязана ни к версии Клода, ни к версии Джемини. Версионирование описывается кортежем трёх независимых версий:

$$C_{A \to B}(V_A, V_B, V_C)$$

Где:
* **$V_A$ (Source Spec Version):** Версия спецификации источника (Claude Code).
* **$V_B$ (Target Spec Version):** Версия спецификации приёмника (Gemini / Antigravity).
* **$V_C$ (Contract Version):** Версия **самого контракта трансляции** между ними.

#### Сценарии независимого изменения версий:
1. **Патч логики трансляции ($V_C \uparrow$):** Ни Anthropic ($V_A=1.0.0$), ни Google ($V_B=2.0.0$) ничего не меняли. Но мы исправили граничный случай в расчёте номеров строк для `replace_file_content` или улучшили детекцию XML. Меняется **только** версия контракта: $C_{A \to B}@1.0.1$.
2. **Вендор А расширил спеку ($V_A \uparrow$):** Anthropic выпустил `agent-skills@1.1.0` с новым полем `icon:`. Google остался на `2.0.0`. Выпускается контракт $C_{A \to B}@1.1.0$, поддерживающий новые метаданные, при сохранении обратной совместимости.
3. **Вендор B совершил мажорный прорыв ($V_B \uparrow$):** Google в `antigravity@3.0.0` добавил нативный строковый `file_patch`. Появляется новый контракт $C_{A \to B}@2.0.0$, ориентированный на пару $(S_A@1.x \to S_B@3.0.0)$, исключающий сложный расчёт строк.

### 13.3. Translation Bus API и Skill Intermediate Representation (SIR)

Посередине между спеками работает типизированная шина конвертации (Translation Bus API), преобразующая ассеты через нейтральное промежуточное представление (**Skill Intermediate Representation — SIR**):

```
┌─────────────────┐
│ Source Skill    │
│ (Claude Format) │
└────────┬────────┘
         │  1. Ingestion via Source Spec (S_A@v)
         ▼
┌────────────────────────────────────────────────────────┐
│  Skill Intermediate Representation (SIR)               │
│  Нейтральное абстрактное дерево:                       │
│  • Intent & Routing Triggers                           │
│  • Required Capabilities: [fs.modify, shell.exec, ...] │
│  • Abstract AST Sections (steps, rules, examples)      │
│  • Resource Manifest (scripts, references)             │
└────────────────────────┬───────────────────────────────┘
                         │  2. Lowering via Contract (C_{A->B}@v)
                         ▼
┌────────────────────────────────────────────────────────┐
│  Target Specialized Model (TSM)                        │
│  Адаптированное дерево под рантайм:                    │
│  • Primitives lowered to Target Tools                  │
│  • Polyfills injected for missing capabilities         │
│  • Dialect adjusted (XML stripped, Alerts applied)     │
└────────────────────────┬───────────────────────────────┘
                         │  3. Emission via Target Spec (S_B@v)
                         ▼
┌─────────────────┐
│ Target Skill    │
│ (Gemini Format) │
└─────────────────┘
```

#### Программный интерфейс (Translation Bus API):

```python
class SkillConverterAPI:
    """Шина контрактной трансляции между спецификациями провайдеров."""

    def validate_source(self, skill_path: Path, spec: SourceSpec) -> SourceValidationReport:
        """Этап 1: Валидирует исходник строго по схеме S_A."""
        ...

    def evaluate_feasibility(
        self, sir: SkillIR, target_spec: TargetSpec, contract: MigrationContract
    ) -> FeasibilityReport:
        """Этап 2: Сверяет требования SIR с возможностями TargetSpec через Contract."""
        ...

    def transform(self, sir: SkillIR, contract: MigrationContract) -> TargetSpecializedModel:
        """Этап 3: Выполняет lowering примитивов и инъекцию полифилов."""
        ...

    def emit(self, tsm: TargetSpecializedModel, target_spec: TargetSpec, dest: Path) -> EmissionResult:
        """Этап 4: Записывает нативные файлы по правилам топологии S_B."""
        ...
```

### 13.4. Декларативный манифест контракта (Declarative Contract Schema)

Контракт миграции — это версионируемый YAML-манифест (`contracts/anthropic_to_antigravity.yaml`):

```yaml
contract_id: anthropic-to-antigravity
version: 1.2.0

# 1. Диапазоны поддерживаемых версий спецификаций (Compatibility Matrix)
compatibility_matrix:
  source:
    provider: anthropic
    spec: agent-skills
    supported_versions: ">=1.0.0 <2.0.0"
  target:
    provider: google
    spec: antigravity-customization
    supported_versions: ">=2.0.0 <3.0.0"

# 2. Семантический маппинг и Lowering возможностей
capability_mappings:
  shell.exec:
    from: "Bash(command)"
    to: "run_command(CommandLine)"
    strategy: exact

  fs.modify:
    from: "FileEdit(path, old_str, new_str)"
    to: "replace_file_content(TargetFile, StartLine, EndLine, TargetContent, ReplacementContent)"
    strategy: adapted
    lowering_rules:
      - calculate_line_bounds: true
      - fallback_warning: "Line calculation is required for Gemini target"

  user.interaction:
    from: "AskUserQuestion"
    to: null
    strategy: polyfill
    polyfill_action: "inject_non_interactive_fallback"
    severity: degradation

# 3. Нормализация диалекта и разметки
dialect_rules:
  xml_tags:
    "<rules>": "## Rules"
    "<guidelines>": "> [!NOTE]"
    "<step n=\"{n}\">": "{n}. "
  strip_tags:
    - "<thinking>"
    - "<scratchpad>"
```

### 13.5. Семантическое версионирование для LLM-контрактов (Agentic SemVer)

В отличие от классического SemVer, где breaking change — это сигнатура функции, для агентских контрактов действуют правила **Agentic SemVer**:

* **PATCH ($1.0.X$):**
  * Исправление дефектов в regex-парсерах или рерайтерах разметки.
  * Уточнение формулировок полифилов без изменения их поведенческой сути.
  * Багфиксы в расчёте номеров строк.
* **MINOR ($1.X.0$):**
  * Поддержка новых опциональных полей из обновленной спецификации источника ($S_A$).
  * Добавление нового полифила для ранее не поддерживаемой второстепенной возможности (повышение Compatibility Score в отчёте).
  * 100% обратная совместимость: любой скилл, компилировавшийся версией $1.0.0$, скомпилируется версией $1.1.0$ с тем же или лучшим качеством.
* **MAJOR ($X.0.0$):**
  * Изменение парадигмы оркестрации (например, переход от синхронного выполнения к реактивным сабагентам).
  * Ужесточение безопасности в `Feasibility Gate` (конструкция, ранее компилировавшаяся как `DEGRADED`, теперь признаётся `INCOMPATIBLE`).
  * Переход на новую мажорную версию спецификации $S_A$ или $S_B$.

### 14.2. Ключевые AI-особенности репозитория

#### А. Принцип Context Hygiene для ИИ-ассистентов
Агент не должен сжигать десятки тысяч токенов контекста при первом же открытии репозитория:
* **`AGENTS.md` (до 150 строк):** Единый компактный источник правил для агентов. Задаёт инварианты кодовой базы (никаких хардкодов тулов в ядре, вся семантика — через `contracts/*.yaml`, строгая типизация `mypy --strict`, английский язык идентификаторов).
* **Симлинки:** Файлы `CLAUDE.md` и `GEMINI.md` делаются симлинками на `AGENTS.md`, исключая рассинхронизацию инструкций.

#### Б. Спецификации и контракты как данные (Data-Driven Engine)
Правила трансляции вынесены из Python-кода в декларативные YAML-манифесты:
* Версии спек вендоров изолированы в `specs/<vendor>/<version>/spec.yaml`.
* Правила трансляции изолированы в `contracts/<source>-to-<target>/<version>.yaml`.
* Кодовая база Python является **универсальным исполнителем контрактов**. Поддержка новой версии Gemini или Claude сводится к добавлению манифеста и Golden Master тестов без вмешательства в логику ядра.

#### В. Строгое разделение `tests/` vs `evals/` (Экономика токенов)
* **`tests/` (Обязательный pre-commit и PR-гейт):**
  * Строгий детерминизм, 0 сетевых запросов, 0 вызовов LLM.
  * Скорость прогона: до 3 секунд на весь набор тестов.
  * Snapshot-тестирование Golden Master (`pytest` + `syrupy`): сверка компиляции фикстур с эталоном байт-в-байт.
* **`evals/` (Периодический релизный гейт):**
  * Запуск вручную (`make eval`) или по расписанию (nightly build).
  * Требует API-ключи провайдеров.
  * Замер поведенческой эквивалентности моделей (Trigger Concordance $\ge 95\%$, Tool Error Rate $= 0\%$).

#### Г. Изоляция выполнения скриптов (Security Sandbox)
Поскольку в скиллах могут содержаться сторонние вспомогательные скрипты (`scripts/`), каталог `evals/` запускается строго в изолированных контейнерах (Docker), защищая хостовую машину разработчика от произвольного исполнения чужого кода.

### 14.3. Рекомендуемый стек технологий

| Компонент | Выбор | Обоснование |
| :--- | :--- | :--- |
| **Менеджер пакетов и окружения** | **`uv`** (Astral) | Молниеносная установка зависимостей (<1 сек), исполнение через `uvx`, замена `poetry` и `pip`. |
| **CLI-фреймворк** | **`typer`** / **`click`** | Декларативный интерфейс командной строки с автогенерацией подсказок. |
| **Форматирование терминала** | **`rich`** | Наглядный вывод таблиц, статусов и отчёта `Feasibility Report` в консоли. |
| **Markdown AST парсер** | **`mistletoe`** / **`markdown-it-py`** | Мощный парсинг разметки в AST с сохранением структуры блоков. |
| **Валидация схем данных** | **`pydantic` v2** | Строгая типизация манифестов спек и контрактов на базе C-расширения. |
| **Линтер и форматтер** | **`ruff`** | Мгновенный статический анализ и автоформатирование кода. |
| **Статическая типизация** | **`mypy`** (strict mode) | Обязательная строгая типизация для узлов AST и контрактов. |
| **Snapshot-тестирование** | **`pytest` + `syrupy`** | Хранение и автоматическое обновление Golden Master слепков. |

### 14.4. Пошаговый чеклист инициализации нового репозитория

# 1. Создание проекта с современным pyproject.toml
uv init --package agent-skill-adapter

# 2. Добавление основных зависимостей
uv add pydantic pyyaml typer rich markdown-it-py

# 3. Добавление инструментов разработки и тестирования
uv add --dev pytest pytest-mock syrupy ruff mypy

touch AGENTS.md
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md GEMINI.md

uv run ruff check .
uv run mypy src/
uv run pytest
